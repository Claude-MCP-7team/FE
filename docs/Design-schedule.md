# 서류·일정 화면 스펙

작성일: 2026-09-19 · 작성: Design · **구현: Frontend**

`#/schedule` 화면의 구현 스펙이다. Design은 이 문서까지 담당하고, 구현은 FE가 한다.
현재 이 화면은 Mock(`mocks/scenario.json`)으로만 동작하며 실서버 연결이 없는 **유일하게 남은 미구현 화면**이다.

상태 표현의 공통 규칙은 [Design-states.md](Design-states.md), 토큰은 [Design-system.md](Design-system.md)를 따른다.
이 문서는 그 규칙을 이 화면에 적용한 것이고, 충돌하면 그 두 문서가 우선이다.

---

## 1. 이 화면이 답하는 질문은 세 개다

BE의 `app/schemas/plan.py` 첫머리가 화면의 목적을 이미 정의해 두었다. 그대로 따른다.

| 질문 | 데이터 |
| --- | --- |
| 지금 당장 움직여야 하는 게 있나 | `summary.urgent`, `plans[].status` |
| 주민센터 한 번에 뭘 떼 오면 되나 | `documents[]` (서류 기준으로 묶은 것) |
| 이 정책은 언제 준비를 시작해야 하나 | `plans[].recommended_start_date` |

세 질문에 답하지 않는 정보는 이 화면에 넣지 않는다.

## 2. 데이터

`POST /v1/plan`. 판정과 마찬가지로 조건이 본문으로 들어가므로 POST다.
응답은 `PlanResponse`이며 `generated_for_date`(KST 기준일), `summary`, `plans[]`, `documents[]`를 담는다.

`plans[]`는 **BE가 착수 급한 순서로 정렬해서 보낸다.** FE는 재정렬하지 않는다.

---

## 3. 화면 구조 — 서류 묶음이 먼저다

```
[기준일 · 요약]
[① 서류 할 일]      ← documents[]  (서류 기준으로 묶인 것)
[② 정책별 일정]      ← plans[]      (착수 급한 순)
[면책]
```

**순서를 바꾸지 않는다.** 마일스톤 FE 항목은 "필요서류 Checklist"를 정책별로 적었지만, BE는 의도적으로 서류 기준으로 묶은 `documents[]`를 따로 보낸다. `DocumentTask` 주석이 이유를 말한다.

> 정책별 목록만 주면 사용자는 주민등록등본을 **정책 수만큼** 떼러 간다. 이 뷰의 존재 이유가 그것이다.

정책별 목록을 먼저 놓으면 사용자는 같은 서류를 중복해서 준비한다. 서류 묶음이 이 화면의 본체다.

### 상단 요약

`generated_for_date`를 **반드시 표시한다.** 모든 날짜가 이 기준일에서 계산된 값이라, 기준일 없이는 어제 본 화면과 오늘 본 화면이 왜 다른지 알 수 없다.

요약에 넣을 것:

- `summary.urgent`가 0보다 크면 가장 먼저, 가장 크게
- `visit_required_count` — 창구 방문이 필요한 서류 수. **온라인으로 끝나는지 사용자가 먼저 알아야 한다**
- `total_document_cost_krw` — 0원이면 "무료"로 쓴다

`summary`의 나머지 건수(`on_track`/`rolling`/`closed`…)는 요약에 넣지 않는다. 목록에서 보이면 충분하고, 6칸 요약은 읽히지 않는다.

---

## 4. 계획 상태 6개

`PlanStatus`는 판정 상태와 **다른 축이다.** `URGENT`/`ON_TRACK`/`ROLLING`/`UNKNOWN`/`CLOSED`/`INFEASIBLE`.

### 판정 상태 4색을 쓰지 않는다

`PASS`/`FAIL`/`UNKNOWN`/`FUTURE_PASS`의 색은 판정 상태만 뜻한다. 계획 상태에 그 색을 쓰면 "조건 미충족"으로 읽힌다.
이 화면에 오는 정책은 **이미 전부 적격**이므로, 빨간 배지는 특히 틀린 신호다.

같은 이유로 `UNKNOWN`이라는 값이 양쪽에 있지만 **뜻이 다르다.** 판정의 `UNKNOWN`은 "사용자 정보가 부족", 계획의 `UNKNOWN`은 "공고에 마감일이 없다"이다. 같은 문구를 쓰지 않는다.

### 표현 규칙

상태는 **사각 태그**(`border-radius: 6px`)로 쓴다. 판정 배지는 알약(24px), 신뢰도 칩은 빈 알약(24px)이므로 형태만으로 구분된다.

| 상태 | 태그 문구 | 표현 |
| --- | --- | --- |
| `URGENT` | 지금 시작 | 주의색 채움 + 카드 좌측 accent |
| `INFEASIBLE` | 기한 부족 | 주의색 채움 + 카드 좌측 accent |
| `ON_TRACK` | 여유 있음 | 중성 (테두리만) |
| `ROLLING` | 상시 모집 | 중성 (테두리만) |
| `UNKNOWN` | 마감일 미확인 | 중성 (테두리만) |
| `CLOSED` | 마감됨 | 중성 + 카드 전체 흐리게 |

색은 둘만 추가한다.

| 용도 | 값 | 대비 |
| --- | --- | --- |
| 주의 태그 | `#8a3d10` on `#fcc9a4` | 5.09 |
| 카드 좌측 accent | `#c2521a` (4px) | 4.65 (흰 배경) |

나머지 넷은 `.chip`과 같은 중성 스타일을 쓴다. **6개에 각각 색을 주지 않는다** — 색이 여섯이면 아무것도 눈에 띄지 않는다. 급한 것만 눈에 띄면 된다.

#### P-2 경위 (2026-09-19 · 피그마에서 확인)

처음 안은 연한 주황(`#8a3d10` on `#ffeadb`)이었다. 컴포넌트 시트에서 판정 `UNKNOWN` 배지와 나란히 놓고 보니 **색이 거의 구분되지 않았다.**

| | 두 배경의 차이 |
| --- | --- |
| `unknown-bg #fff3dc` vs 첫 안 `#ffeadb` | **1.059** |
| 두 글자색 `#775013` vs `#8a3d10` | 1.067 |

원인은 밝기가 아니라 **색상이 인접**한 것이었다. 노랑과 옅은 주황은 색상환에서 붙어 있고, 판정 4색은 원래 밝기가 서로 1.00~1.07로 비슷하다(초록/빨강/노랑/파랑이 색상으로 갈리고 기호·문구가 붙는 구조다). 그래서 옅은 주황은 노랑 배지의 변종처럼 읽혔다.

**같은 주황을 진하게 해서 해결했다.** `#ffeadb` → `#fcc9a4`.

| | 값 |
| --- | --- |
| 글자 대비 | 5.09 (기준 4.5) |
| `unknown-bg`와 차이 | **1.362** (이전 1.059) |
| 흰 카드와 차이 | 1.497 |

색상을 옮기지 않고 채도·명도만 올린 이유는, **긴급 상태에는 주황이 의미상 맞고** 판정 4색(초록·빨강·노랑·파랑) 중 어느 것과도 겹치지 않는 유일한 계열이기 때문이다. 파란 계열도 검토했으나 `FUTURE_PASS`와 같은 계열이 되어, "향후 가능"(나중)과 "지금 시작"(당장)이 시간 의미가 정반대인데 색을 공유하게 되므로 쓰지 않았다.

진해진 만큼 눈에 띄는데, 이것이 의도다. 이 태그는 **급한 것만 눈에 띄게 하는 장치**다.

### `reason`을 그대로 쓴다

`PolicyPlan.reason`은 BE가 **"화면이 그대로 노출해도 되는 문장"**으로 만든 값이다. 요약하거나 다시 쓰지 않는다.

예: `2026-11-03 까지 서류 준비를 시작하면 됩니다 (여유 영업일 12일).`

`reason`에는 유효기간 경고와 추정 표시가 뒤에 덧붙는다. 잘라내지 않는다.

## 5. 서류 할 일 (`documents[]`)

각 항목이 담아야 할 것:

| 표시 | 필드 | 규칙 |
| --- | --- | --- |
| 서류명 | `name` | |
| 어디서 | `issuer`, `channel` | |
| 며칠 걸리나 | `lead_time_business_days`, `lead_time_min_business_days` | **범위가 있으면 범위로 쓴다** (예: 영업일 1~5일). 역산에는 최댓값이 쓰였다 |
| 어느 정책에 쓰나 | `required_by_titles` | 정책 ID가 아니라 제목을 쓴다 |
| 언제까지 | `needed_by_date` | 이 서류를 요구하는 정책 중 가장 이른 착수일 |
| 비용 | `cost_krw` | |

### 반드시 표시해야 하는 세 가지

**① `requires_visit` — 창구 방문**

주석: "하루를 통째로 써야 하는 일이다." 온라인 발급과 같은 무게로 보이면 안 된다. 목록에서 바로 구분되게 한다.

**② `issue_not_before` — 너무 일찍 떼면 안 된다**

이 화면에서 가장 낯선 개념이다. 사용자는 "서류는 미리 떼면 좋다"고 생각한다.
유효기간이 있는 서류는 이 날짜 **이전에 발급하면 제출일에 만료된다.**

문구 예: `2026-10-15 이후에 발급하세요. 그 전에 떼면 제출일에 만료됩니다.`

"~까지"와 "~이후"가 한 화면에 섞이므로, 두 날짜가 시각적으로 구분되게 놓는다.

**③ `single_issue_covers_all: false` — 나눠 떼야 한다**

한 번 떼서 모든 정책에 쓸 수 없는 경우다. 이 표시가 없으면 사용자는 한 번 떼고 나중에 만료된 걸 들고 간다.

문구 예: `정책마다 따로 발급해야 해요.`

### 체크 상태 【결정 필요 · P-1】

마일스톤 FE 항목은 "서류 Checklist"라고 적었지만 **BE는 체크 상태를 저장하지 않는다.**

- **선택지 A** — 체크박스를 넣고 브라우저에만 저장한다. 기기를 바꾸면 사라진다
- **선택지 B** — 체크박스를 넣지 않는다. 목록과 날짜만 보여준다
- **선택지 C** — 체크박스를 넣되 저장하지 않는다고 명시한다

저장되지 않는 체크박스는 사용자가 저장된다고 믿게 만든다. **B 또는 C를 권한다.**

## 6. 확정으로 보이면 안 되는 것

이 화면의 날짜는 전부 계산값이다. 네 가지 경우에 확정으로 표시하면 사용자가 마감을 놓친다.

| 필드 | 뜻 | 표시 |
| --- | --- | --- |
| `lead_time_estimated` | 이 서류의 발급 소요일이 추정 | 서류 항목에 칩 |
| `estimated` | 이 정책 역산에 추정치가 섞임 | 정책 카드에 칩 |
| `outside_calendar_coverage` | 공휴일표가 덮지 않는 구간을 계산 | 정책 카드에 칩 |
| `master_unverified` | 서류 마스터 값이 미검증 | 서류 항목에 칩 |

**[Design-states.md](Design-states.md) S-4의 중성 칩을 그대로 쓴다.** 신뢰도와 같은 성격이므로 같은 형태를 쓴다.

문구는 `src/confidence.js`와 같은 어법으로 짧게 둔다. 예: `추정 포함`, `미검증`.

`UNKNOWN`·`estimated` 정책에는 `dept_name`·`dept_tel`이 함께 온다. 판정 상세와 같은 `.notice-inline`으로 표시한다.

`unverified_document_count`가 0보다 크면 상단 요약에도 한 줄 넣는다.

## 7. 날짜 문구

- 모든 날짜는 **영업일 기준 계산값**이다. "영업일"이라는 말을 생략하지 않는다
- `recommended_start_date`는 "준비를 시작하는 날"이지 신청일이 아니다
- `deadline_date`는 공고 마감일이다. 판정 화면의 `future_eligible_from`(조건 충족 예상일)과 **다른 값**이므로 같은 문구를 쓰지 않는다
- `slack_business_days`가 음수면 이미 지난 것이다. 음수를 그대로 노출하지 않는다

## 8. 상태

| 상태 | 처리 |
| --- | --- |
| Loading | 기존 화면과 같은 `.state` |
| Error | `.state` + 다시 시도. 판정·조합 화면과 같은 어법 |
| 프로필 없음 | 프로필 저장으로 보내는 안내 |
| Empty (`plans[]` 비어 있음) | "신청할 수 있는 정책이 아직 없어요" + 판정 결과로 돌아가는 경로 |
| 서류가 없는 정책 | 일정만 표시. 빈 서류 목록을 만들지 않는다 |

`disclaimer`는 응답에 포함되므로 화면 하단에 그대로 노출한다.

## 9. 접근성

- 날짜는 `<time>`으로 감싼다
- 서류 묶음과 정책 일정은 각각 `<section>` + 제목을 갖는다
- 상태 태그는 색만으로 구분되지 않는다. 문구가 항상 함께 있다 (위 4장 표)
- `CLOSED` 카드를 흐리게 처리할 때 **글자 대비가 4.5:1 아래로 내려가면 안 된다.** 투명도 대신 중성색을 쓴다
- 새 색 두 개의 대비는 4장에 계산해 두었다

## 12. 구현 순서 제안

1. `POST /v1/plan` 클라이언트 + 응답 검증 (판정·조합과 같은 구조)
2. 서류 할 일 목록 — **이게 화면의 본체다**
3. 정책별 일정 목록
4. 상단 요약
5. 추정·미검증 칩, 담당부서 안내
6. 상태(Loading/Error/Empty)

**2번까지만 되어도 화면의 목적은 선다.** 시간이 부족하면 4번 이후를 줄인다.
