# 판정 상태 · 근거 표현 규격

갱신일: 2026-09-19 · 작성: Design · **초안, 결정 대기 항목 있음**

Milestone 11장 "반드시 고정할 인터페이스 4개" 중 **4번 `Design ↔ FE: 상태·근거 표현 규격`**에 해당하는 문서다.
판정 상태와 근거 UI를 화면마다 다르게 만들지 않기 위한 단일 기준이며, 판정 로직 자체는 정의하지 않는다.

이 문서의 결정 항목(S-1 ~ S-6)은 아직 비어 있다. **채워지기 전까지 FE는 해당 부분을 구현하지 않는다.**

## 1. 서버가 주는 값 (PRD 기준)

정책 단위 판정은 **두 축**으로 온다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| `verdict` | `ELIGIBLE` | 조건을 충족한다 |
| | `INELIGIBLE` | 조건을 충족하지 못한다 |
| | `NEEDS_INFO` | **사용자 정보**가 부족해 판정할 수 없다 |
| `confidence` | `CONFIRMED` | 원문 근거로 확정된 판정 |
| | `ESTIMATED` | 추정이 섞인 판정 |
| | `NEEDS_REVIEW` | **공고문·근거** 자체에 추가 검토가 필요하다 |

조건 단위 상태는 별도로 `PASS / FAIL / UNKNOWN / FUTURE_PASS` 4개다 (PRD 13장).

> **주의**: `NEEDS_INFO`는 *사용자가 답하면 풀리는 것*, `NEEDS_REVIEW`는 *사용자가 무엇을 해도 풀리지 않는 것*이다.
> 사용자의 다음 행동이 완전히 다르므로 같은 표현으로 뭉개지 않는다.

## 2. 화면 분류 4개 (현재 구현값)

`src/contracts.js`의 `statuses`가 쓰는 값이다. 색은 `src/styles.css`에 정의돼 있다.

> **조건 수준과 정책 수준 모두 4개를 쓴다.** 정책 수준의 `FUTURE_PASS`는 BE의 `future_eligible_from`이 결정한다 (S-1 · S-2).

| 키 | 문구 | 기호 | 글자색 | 배경색 | 다음 행동 |
| --- | --- | --- | --- | --- | --- |
| `PASS` | 신청 가능 | `✓` | `#135f3c` | `#dceee2` | 근거 확인 후 서류 준비 |
| `FAIL` | 조건 미충족 | `×` | `#993d36` | `#fae9e6` | 미충족 이유 확인 |
| `UNKNOWN` | 추가 확인 | `?` | `#775013` | `#fff3dc` | 추가 질문 답변 |
| `FUTURE_PASS` | 향후 가능 | `↗` | `#325975` | `#e5edf8` | 예상 충족일 확인 |

색만으로 구분하지 않고 **기호와 문구를 항상 함께** 제공한다. 위 4쌍의 명도 대비는 모두 WCAG AA를 통과한다 ([Design-system.md](Design-system.md) 6장).

## 3. 현재 구현 실태 (2026-09-19 dev 기준)

**이 문서를 쓰기 시작한 시점 이후, `dev`가 판정 API를 화면에 연결하면서 아래 항목들을 코드로 먼저 결정했다.**
합의된 규격이 아니라 구현 과정의 기본값이므로, 아래 S 항목은 "정할 것"이 아니라 **"이대로 확정할지, 바꿀지"**를 정하는 것이 된다.

`src/judgement-page.js`가 실제로 하는 일:

| 항목 | 현재 구현 | 위치 |
| --- | --- | --- |
| 정책 `verdict` → 배지 | `ELIGIBLE`→PASS / `INELIGIBLE`→FAIL / `NEEDS_INFO`→UNKNOWN | `verdicts` 상수 |
| 정책 수준 `FUTURE_PASS` | ~~쓰지 않음~~ → **`future_eligible_from`으로 연결** (S-1·S-2) | `judgement-contract.js` |
| Dashboard 집계 | ~~3칸~~ → **4칸** (향후 가능 추가, 조건 미충족에서 차감) | `renderJudgementDashboard` |
| `confidence` 표시 | ~~UNKNOWN 색 배지 + enum 원문~~ → **중성 칩 + 한국어 문구** (S-4에서 수정) | 같은 함수 |
| 조건 status | matched→PASS / unmatched+`satisfiable_from`→FUTURE_PASS / unmatched→FAIL / unknown→UNKNOWN | `judgement-contract.js` |
| 근거 URL | `rule.source_url` → 없으면 `result.origin_url` → 없으면 표시 안 함 | `toJudgementView` |
| 정책 제목 | ~~`policy_id` 원문~~ → **`title` 수용, 없으면 식별자 표시** (S-5) | `renderJudgementDetail` |

### 확정된 것 (그대로 둔다)

조건 수준 4상태 매핑과 근거 URL 대체 규칙은 **BE 응답 구조에 근거한 결정**이므로 유지한다.
`validateJudgementResponse()`가 원문 인용문 부재는 거부하고 URL 부재만 허용하는 것도 "근거 없는 확정 금지" 원칙과 맞는다.

### 문제가 되는 것

**(가) 신뢰도가 판정 상태의 색 언어를 빌려 썼다** — S-4에서 해소했다

`ELIGIBLE` + `ESTIMATED` 정책에 녹색 "신청 가능" 배지와 **노란 배지**가 함께 붙었다.
노란색은 이 서비스에서 `UNKNOWN`(추가 확인)을 뜻하므로 사용자가 두 축을 구분하지 못했다.
중성 칩으로 바꿔 판정 상태 4색이 판정 상태만 뜻하도록 했다.

**(나) enum 원문이 그대로 노출됐다** — S-4에서 해소했다

배지에 `ESTIMATED`, `NEEDS_REVIEW`가 영어 대문자로 찍혔다. 한국어 문구로 바꿨다.

**(다) 정책 제목이 `policy_id`였다** — S-5에서 부분 해소했다

내부 ID가 정책 이름인 것처럼 제목 자리에 놓여 있었다. 식별자로 보이도록 바꾸고 `title` 수용 경로를 열었다. 실제 이름이 나오려면 BE 변경이 필요하다.

**(라) `FUTURE_PASS`가 목록에서 보이지 않았다** — S-1 · S-2에서 해소했다

Dashboard가 `verdict` 3개만 그려 "지금은 안 되지만 언제 되는지"가 목록에서 사라졌다.
BE의 `future_eligible_from`을 읽어 네 번째 배지와 집계 칸을 연결했다.

주의할 점은 **조건 하나가 `FUTURE_PASS`라고 정책이 `FUTURE_PASS`가 아니라는 것**이다. 연령 상한처럼 영구 불가 조건이 함께 있으면 BE는 날짜를 주지 않는다. FE가 조건에서 날짜를 집계했다면 "3년 기다리면 된다"는 틀린 안내를 했을 것이다.

## 4. 결정 항목

### S-1 · 정책 수준 매핑 【확정 · 2026-09-19】

**결정: `verdict` 3개는 그대로 두고, 네 번째 분류는 BE의 `future_eligible_from`으로 그린다.**

| `verdict` | `future_eligible_from` | 화면 분류 |
| --- | --- | --- |
| `ELIGIBLE` | — | `PASS` 신청 가능 |
| `NEEDS_INFO` | — | `UNKNOWN` 추가 확인 |
| `INELIGIBLE` | 있음 | `FUTURE_PASS` 향후 가능 |
| `INELIGIBLE` | 없음 | `FAIL` 조건 미충족 |

`confidence`는 매핑에 **쓰지 않는다.** 다른 축이므로 중성 칩으로 따로 표시한다(S-4).
조건 수준 규칙과 같은 모양이라 두 층위가 같은 어법으로 읽힌다.

### S-2 · `FUTURE_PASS` 신호 【확정 · 2026-09-19】

**BE가 이미 제공하고 있었다.** 선택지 A(표시용 필드 요청)가 구현된 상태였고 FE가 읽지 않고 있었을 뿐이다.

`app/schemas/judgement.py`:

- `JudgementResult.future_eligible_from` — "마일스톤이 말하는 네 번째 판정 상태를 화면이 그릴 수 있는 단일 신호"
- `JudgementSummary.future_eligible` — "화면의 네 번째 배지가 쓰는 값"

BE가 `verdict`를 네 값으로 늘리지 않은 이유도 주석에 있다. `verdict`는 "오늘 자격이 있는가"이고 이 날짜는 "언제부터 있는가"라, 한 필드에 섞으면 FE가 필터와 배지 중 어느 뜻으로 쓸지 정할 수 없게 된다.

#### 날짜가 채워지는 조건 (BE 보장)

미충족 조건이 **전부** 시간으로 해결될 때만 채운다. 하나라도 아래에 해당하면 `null`이다.

- 시간과 무관한 조건 (소득·가구원수)
- 영구 불가 (연령 상한 초과)
- 미확인 조건이 남아 있음
- **그날 다른 조건이 깨지는 경우** — 24세 사용자에게 거주 36개월을 요구하면서 연령 상한이 25세인 정책은, 거주 요건을 채우는 날 이미 나이가 넘는다

날짜는 조건들 중 **가장 늦은** 날이며, BE가 그 날짜로 전 조건을 다시 평가해 검증한다.

그래서 **조건 하나가 `FUTURE_PASS`라고 정책이 `FUTURE_PASS`가 되지 않는다.** 이 구분이 (라)의 답이다. FE는 조건에서 날짜를 집계하지 않고 BE가 준 값만 읽는다.

#### 집계 칸

`future_eligible`은 별도 분류가 아니라 **`ineligible`의 부분집합**이다. 그대로 네 칸을 만들면 합이 전체를 넘는다.

카드 하나에 배지가 하나씩 붙으므로 **집계 칸도 배지와 1:1로 맞춘다.**

| 칸 | 값 |
| --- | --- |
| 신청 가능 | `summary.eligible` |
| 조건 미충족 | `summary.ineligible - summary.future_eligible` |
| 추가 확인 | `summary.needs_info` |
| 향후 가능 | `summary.future_eligible` |

네 칸의 합이 전체 정책 수와 같다.

#### 날짜 문구

**접수 가능일로 표현하지 않는다.** 조건이 충족되는 날일 뿐 공고 접수기간과 무관하다.
카드는 "예상 충족일", 상세는 "예상 충족일 · 접수 기간은 공고에서 따로 확인해 주세요"로 쓴다.

#### 아직 안 된 것

- **상태 필터** — 실판정 Dashboard에는 필터가 없다. Mock 화면에만 있다. 분류가 넷이 된 지금 필터가 의미를 갖는다.
- **`needs_review_fields`** — BE가 "무엇을 확인 못 했는지"를 필드명 목록으로 보내는데 화면에 표시되지 않는다. 주석: "confidence 만 낮추면 '왜 확인이 필요한지'를 답할 수 없다." 필드명이 내부 표기(무주택·세대주·보증금 등)라 **사용자 문구 매핑이 필요하다.** 별도 결정 항목이다.

### S-3 · `NEEDS_INFO`와 `NEEDS_REVIEW`를 구분하는가 【미정】

현재는 둘 다 노란 계열로 보여 구분되지 않는다. 사용자의 다음 행동이 정반대인데도 그렇다.

- **선택지 A** — 배지는 `UNKNOWN` 하나로 두고 **다음 행동 버튼**으로만 구분한다.
  (`NEEDS_INFO` → "추가 질문 답하기" / `NEEDS_REVIEW` → 버튼 없이 담당부서 연락처)
  - 현재 상세 화면이 `NEEDS_REVIEW`에 담당부서 연락처를 이미 노출하고 있어 이 방향과 가깝다.
- **선택지 B** — 별도 배지를 추가해 분류를 늘린다.
- **선택지 C** — 배지는 같게 두고 카드에 보조 라벨 한 줄을 붙인다.

### S-4 · `ESTIMATED` · `NEEDS_REVIEW` 표시 【확정 · 2026-09-19】

**결정: 색 없는 중성 칩 (선택지 A).** 신뢰도는 판정 상태와 다른 시각 언어를 쓴다.

판정 상태 4색은 **오직 판정 상태만** 뜻한다. 신뢰도는 테두리만 있는 중성 칩으로 표시해 두 축이 절대 겹치지 않게 한다.

| 항목 | 값 |
| --- | --- |
| 형태 | 알약형(`border-radius:24px`), 배경 없음, 1px 테두리 |
| 테두리 | `var(--line-strong)` `#7d8f84` — 흰 배경 대비 3.42 |
| 글자 | `#4f5c54` 13px/600 — 흰 배경 대비 7.02, 페이지 배경 6.51 |
| 클래스 | `.chip` |

배지(`.badge`)는 **채워진** 알약, 칩(`.chip`)은 **비어 있는** 알약이다. 형태로도 위계가 구분된다.

#### 사용자 문구

| `confidence` | 칩 문구 | 카드 안내 문구 |
| --- | --- | --- |
| `CONFIRMED` | 표시하지 않음 | 없음 |
| `ESTIMATED` | 추정 포함 | 일부 조건은 추정입니다. 판정 근거를 확인해 주세요. |
| `NEEDS_REVIEW` | 담당부서 확인 | 공고문 근거에 확인이 필요합니다. 담당부서로 문의해 주세요. |

`NEEDS_REVIEW`의 문구는 문서 초안의 예시였던 "확인 필요" 대신 **"담당부서 확인"**을 쓴다.
`UNKNOWN` 배지 문구가 이미 "추가 확인"이라 너무 비슷해 다시 혼동을 만들기 때문이고, 사용자가 할 행동을 직접 가리키는 편이 낫기 때문이다. 바꾸고 싶으면 `confidenceLabels` 한 줄만 고치면 된다.

#### 중복 문구 해소

기존 Dashboard는 신뢰도 배지와 "판정 신뢰도: `ESTIMATED` · 담당부서 확인이 필요합니다" 문구를 **함께** 보여줬다.
칩이 상태를 이미 말하므로, 안내 문구는 enum을 반복하지 않고 **무엇을 하면 되는지**만 말하도록 위 표처럼 바꿨다.

#### 적용 범위

`src/judgement-page.js`의 Dashboard 카드와 정책 상세 모두에 적용했다.
상세의 담당부서 연락처(`.notice-inline`)는 구체적인 정보이므로 칩과 중복이 아니며 그대로 둔다. 이 요소에도 같은 중성 계열 스타일을 정의했다.

#### 남은 확인

**브라우저에서 칩이 배지와 충분히 구별되는지 실제로 봐야 한다.** 대비값은 계산으로만 검증했다.

### S-5 · 정책 제목 【부분 확정 · 2026-09-19 · BE 변경 필요】

카드·상세 제목이 `policy_id` 원문이었다. BE `dev`의 `app/schemas/judgement.py`를 확인한 결과
**`JudgementResult`에 정책명 필드가 없다.** `policy_id`, `verdict`, `confidence`, `explanation`, 담당부서 필드만 있다.

#### FE 단독 우회가 모두 나쁜 이유

| 방법 | 문제 |
| --- | --- |
| `GET /v1/policies/{id}`를 정책마다 호출 | 이 API는 룰과 근거 인용까지 포함한 **전문**을 반환한다. `app/schemas/catalog.py` 주석이 "목록이 요약만 내보내는" 이유로 이 무게를 든다. 제목 하나 때문에 카드 수만큼 전문을 받는다 |
| `GET /v1/policies` 목록으로 맵 구성 | `limit` 최대 100, id 필터 없음, 실스냅샷 1,555건. 판정된 정책만 고를 수 없다 |

**BE가 판정 시점에 이미 `policy.title`을 들고 있다** (`_summarize()`가 같은 값을 쓴다). 한 필드를 응답에 싣는 것이 맞다.

#### FE가 한 것

- `JudgementResult.title`이 오면 제목으로 쓴다. 검증기는 문자열이 아니면 거부한다.
- 없으면 `policy_id`를 **식별자로** 표시한다. 고정폭·작은 글자·중성색·테두리(`code.policy-ref`).

`policy_id`를 그냥 제목 자리에 넣으면 **그것이 정책 이름인 것처럼 읽힌다.** 식별자로 보이게 하면 사용자가 "이름을 못 받아왔구나"로 읽는다. 제목이 없다는 사실을 숨기지 않는 것이 이번 처리의 요점이다.

BE가 `title`을 보내기 시작하면 FE 변경 없이 제목이 나온다.

**BE 요청 사항:** `JudgementResult`에 `title: str` 추가.

## 5. 근거(Evidence) 표시 규격

모든 판정은 원문 근거와 연결돼야 한다 (Milestone 11장, 가장 중요한 품질 기준).

현재 구현(`renderJudgementDetail`)은 조건마다 `<blockquote>`에 `source_quote`를 넣고, URL이 있을 때만 "원문 보기" 링크를 덧붙인다.
스타일: 배경 `#f5f7f3`, 좌측 `3px solid #135f3c`, 패딩 16px.

### 확정된 것 (그대로 둔다)

- **원문 인용은 우리가 쓴 문장과 분리한다.** 같은 문단에 이어 붙이지 않는다.
  조합의 제외 사유는 인용문이 설명 문장 끝에 붙어 있어 어디까지가 서비스의 말이고 어디부터가 공고문인지 알 수 없었다. 2026-09-19에 별도 인용 블록으로 분리했다.
- URL은 `rule.source_url` → `result.origin_url` → `null` 순으로 대체한다.
- **인용문 부재는 응답을 거부하고, URL 부재만 허용한다.** 근거 없는 확정 금지 원칙과 맞는다.
- 인용문은 원문 그대로 보여준다. 요약하거나 다듬지 않는다.
- 근거 없는 금액·기간·조건을 화면에 노출하지 않는다.

### S-6 · 원문 URL이 없을 때 【미정】

현재는 링크를 **그냥 생략**한다. 사용자는 링크가 없는 이유를 알 수 없다.

- **선택지 A** — 현재대로 생략한다. (시각적으로 가장 조용하다)
- **선택지 B** — "원문 링크 없음"을 명시한다.
- **선택지 C** — URL이 없는 근거를 신뢰도 표시와 연결한다 (S-4와 함께).

**결정:** _(미정)_

### S-7 · 긴 인용문 처리 【미정】

현재는 길이 제한 없이 전문을 표시한다. 조건이 많은 정책에서 상세 화면이 매우 길어진다.

- **선택지 A** — 현재대로 전문을 항상 표시한다.
- **선택지 B** — N줄에서 자르고 "더 보기"로 펼친다. (N = _미정_)
- **선택지 C** — 핵심 문장만 표시하고 원문 링크로 넘긴다.

**결정:** _(미정)_

### 조건 상세의 빈 문구

현재 조건 설명 `<p>`는 `FUTURE_PASS`(예상 충족일) 또는 영구 불충족일 때만 내용이 있고, 그 외에는 **빈 문단**이 남는다.
일반 `FAIL`·`PASS` 조건에 어떤 설명을 넣을지 정해야 한다 (빈 문단 자체를 없앨지 포함).

## 6. 카피 원칙

### `INELIGIBLE`을 Dead End로 만들지 않는다

PRD 2.1의 유지 항목이다. 조건 미충족 화면은 **거절 통보로 끝나면 안 된다.**

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| "신청할 수 없습니다" | "지금은 OO 조건이 맞지 않아요" |
| "자격 미달" | "OO이 △△이면 신청할 수 있어요" |
| 이유 없는 실패 | 미충족 조건 + 원문 근거 + 다음에 볼 것 |

`FAIL` 카드에서 항상 함께 제공할 것 (무엇을 넣을지는 _미정_):

- [ ] 어떤 조건 때문인지
- [ ] 향후 충족 가능한 조건인지 (S-2와 연결)
- [ ] 대안 정책으로 가는 경로

### 확정을 단정하지 않는다

- 중복수혜 확인 전에는 수혜 가능 조합이나 총 혜택 금액을 확정하지 않는다.
- 추정이 섞인 판정을 확정 문구로 쓰지 않는다.
- **추정이 섞인 것은 판정만이 아니다.** 조합의 제외 사유(`excluded[].confidence`)도 `ESTIMATED`일 수 있다.
  2026-09-19 이전에는 이 값이 화면에 전혀 표시되지 않아 추정 충돌이 확정된 제외처럼 보였다. S-4의 중성 칩을 같은 방식으로 적용했다.

### Design이 확인해야 할 미적용 스타일

새 화면들이 쓰는 아래 클래스에 **CSS 규칙이 없다.** 마크업에만 있고 스타일이 붙지 않은 상태다.

| 클래스 | 쓰이는 곳 |
| --- | --- |
| `.judgement-summary` | Dashboard 요약 3칸 |
| `.judgement-card` | 정책 카드 |
| `.question-card` | 역질문 카드 |
| `.conflict` | 조합 충돌 표시 |
| `.notice-inline` | 담당부서 확인 안내 |

`.card`·`.summary` 같은 공통 클래스와 함께 쓰여 기본 형태는 잡히지만, **구분을 위해 추가된 클래스가 아무 일도 하지 않는다.**
각 클래스에 스타일을 정의할지, 마크업에서 뺄지 정해야 한다. 특히 `.conflict`와 `.notice-inline`은 의미상 시각적 구분이 필요해 보인다.
