# 판정 상태 · 근거 표현 규격

갱신일: 2026-09-19 · 작성: Design · **초안, 결정 대기 항목 있음**

Milestone 11장 "반드시 고정할 인터페이스 4개" 중 **4번 `Design ↔ FE: 상태·근거 표현 규격`**에 해당하는 문서다.
판정 상태와 근거 UI를 화면마다 다르게 만들지 않기 위한 단일 기준이며, 판정 로직 자체는 정의하지 않는다.

이 문서의 결정 항목(S-1 ~ S-6)은 아직 비어 있다. **채워지기 전까지 FE는 해당 부분을 구현하지 않는다.**

| ID | 내용 | 결정 주체 | 우선순위 |
| --- | --- | --- | --- |
| S-4 | `ESTIMATED`/`NEEDS_REVIEW`를 상태색과 분리해 표시 | Design | **높음** — 현재 오해를 만드는 구현 |
| S-1 | 정책 수준 매핑을 3분류로 확정할 것인가 | Design + BE | 높음 |

전부 미정이다. **S-4가 가장 급하다** — 지금 화면이 신뢰도를 판정 상태의 색으로 보여주고 있어, 고치지 않으면 사용자가 잘못 읽는다.

## 1. 서버가 주는 값 (PRD 기준)

정책 단위 판정은 **두 축**으로 온다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| `verdict` | `ELIGIBLE` | 조건을 충족한다 |
| | `INELIGIBLE` | 조건을 충족하지 못한다 |
| | `NEEDS_INFO` | **사용자 정보**가 부족해 판정할 수 없다 |
| `confidence` | `CONFIRMED` | 원문 근거로 확정된 판정 |
| | `ESTIMATED` | 추정이 섞인 판정 |
| | `NEEDS_REVIEW` | **공고문·근거** 자체에 추가 검토가 필요하다 |

조건 단위 상태는 별도로 `PASS / FAIL / UNKNOWN / FUTURE_PASS` 4개다 (PRD 13장).

> **주의**: `NEEDS_INFO`는 *사용자가 답하면 풀리는 것*, `NEEDS_REVIEW`는 *사용자가 무엇을 해도 풀리지 않는 것*이다.
> 사용자의 다음 행동이 완전히 다르므로 같은 표현으로 뭉개지 않는다.

## 2. 화면 분류 4개 (현재 구현값)

`src/contracts.js`의 `statuses`가 쓰는 값이다. 색은 `src/styles.css`에 정의돼 있다.

> **조건 수준에서는 4개가 모두 쓰이고, 정책 수준에서는 `FUTURE_PASS`를 제외한 3개만 쓰인다.** 3장 참고.

| 키 | 문구 | 기호 | 글자색 | 배경색 | 다음 행동 |
| --- | --- | --- | --- | --- | --- |
| `PASS` | 신청 가능 | `✓` | `#135f3c` | `#dceee2` | 근거 확인 후 서류 준비 |
| `FAIL` | 조건 미충족 | `×` | `#993d36` | `#fae9e6` | 미충족 이유 확인 |
| `UNKNOWN` | 추가 확인 | `?` | `#775013` | `#fff3dc` | 추가 질문 답변 |
| `FUTURE_PASS` | 향후 가능 | `↗` | `#325975` | `#e5edf8` | 예상 충족일 확인 |

색만으로 구분하지 않고 **기호와 문구를 항상 함께** 제공한다. 위 4쌍의 명도 대비는 모두 WCAG AA를 통과한다 ([Design-system.md](Design-system.md) 6장).

## 3. 현재 구현 실태 (2026-09-19 dev 기준)

**이 문서를 쓰기 시작한 시점 이후, `dev`가 판정 API를 화면에 연결하면서 아래 항목들을 코드로 먼저 결정했다.**
합의된 규격이 아니라 구현 과정의 기본값이므로, 아래 S 항목은 "정할 것"이 아니라 **"이대로 확정할지, 바꿀지"**를 정하는 것이 된다.

`src/judgement-page.js`가 실제로 하는 일:

| 항목 | 현재 구현 | 위치 |
| --- | --- | --- |
| 정책 `verdict` → 배지 | `ELIGIBLE`→PASS / `INELIGIBLE`→FAIL / `NEEDS_INFO`→UNKNOWN | `verdicts` 상수 |
| 정책 수준 `FUTURE_PASS` | **쓰지 않음.** 조건 수준에만 존재 | — |
| Dashboard 집계 | **3칸** (신청 가능 / 조건 미충족 / 추가 확인) | `renderJudgementDashboard` |
| `confidence` 표시 | `CONFIRMED`이면 없음, 아니면 **UNKNOWN 색 배지 + enum 원문** | 같은 함수 |
| 조건 status | matched→PASS / unmatched+`satisfiable_from`→FUTURE_PASS / unmatched→FAIL / unknown→UNKNOWN | `judgement-contract.js` |
| 근거 URL | `rule.source_url` → 없으면 `result.origin_url` → 없으면 표시 안 함 | `toJudgementView` |
| 정책 제목 | **`policy_id` 원문** (정책명 아님) | `renderJudgementDetail` |

### 확정된 것 (그대로 둔다)

조건 수준 4상태 매핑과 근거 URL 대체 규칙은 **BE 응답 구조에 근거한 결정**이므로 유지한다.
`validateJudgementResponse()`가 원문 인용문 부재는 거부하고 URL 부재만 허용하는 것도 "근거 없는 확정 금지" 원칙과 맞는다.

### 문제가 되는 것

**(가) 신뢰도가 판정 상태의 색 언어를 빌려 쓴다**

`ELIGIBLE` + `ESTIMATED` 정책은 **녹색 "신청 가능" 배지 옆에 노란 배지**가 붙는다.
노란색은 이 서비스에서 `UNKNOWN`(추가 확인)을 뜻하므로, 사용자는 두 축을 구분하지 못하고 "가능한가, 확인이 필요한가"로 읽는다.
서로 다른 두 축에 같은 색을 쓰면 안 된다. **S-4에서 반드시 해소해야 한다.**

**(나) enum 원문이 사용자에게 그대로 노출된다**

배지에 `ESTIMATED`, `NEEDS_REVIEW`가 영어 대문자로 찍힌다. 사용자 문구가 필요하다.

**(다) 정책 제목이 `policy_id`다**

상세·카드 제목에 내부 ID가 노출된다. 정책명 필드를 BE에 요청하거나 정책 조회 API와 연결해야 한다.

**(라) `INELIGIBLE`인데 조건에 `FUTURE_PASS`가 있는 경우**

Dashboard에서는 빨간 "조건 미충족"으로만 보이고, 상세에 들어가야 "향후 가능" 조건이 보인다.
"지금은 안 되지만 언제 되는지"가 목록에서 사라진다 — PRD 2.1의 `FUTURE_PASS` 개념 유지와 충돌한다. **S-2의 실질 쟁점이다.**

## 4. 결정 항목

### S-1 · 정책 수준 매핑을 3분류로 확정하는가 【미정】

현재 구현은 `confidence`를 매핑에서 제외하고 `verdict` 3개를 그대로 3분류로 쓴다.

- **선택지 A** — 현재 구현을 확정한다. 화면 분류는 3개, `confidence`는 별도 축으로 표시(S-4).
  - 장점: 이미 동작한다. BE 응답과 1:1이라 FE에 판정 로직이 없다.
  - 단점: `FUTURE_PASS`가 Dashboard에서 사라진다((라) 참고).
- **선택지 B** — `FUTURE_PASS`를 되살려 4분류로 만든다. S-2와 함께 결정.
- **선택지 C** — `confidence`가 `NEEDS_REVIEW`인 경우를 별도 분류로 뺀다.
  - `ELIGIBLE` + `NEEDS_REVIEW`를 녹색 "신청 가능"으로 보여주는 것이 맞는지가 쟁점이다.

**결정:** _(미정)_

> 제약 (PRD·Milestone에서 이미 고정): 원문 근거 없는 조건은 자동 확정하지 않는다. `UNKNOWN`을 임의로 `PASS`로 바꾸지 않는다. `ESTIMATED`를 확정 판정으로 표시하지 않는다.

### S-2 · `FUTURE_PASS`를 정책 수준에서 살릴 것인가 【미정】

BE `verdict`에는 "향후 가능"이 없다. 조건 수준에만 `satisfiable_from`이 있다.
`judgement-contract.js`의 주석이 명시하듯 FE는 **정책 전체의 미래 날짜를 만들어내지 않는다** — 이 경계는 지킨다.

- **선택지 A** — BE에 정책 수준 표시 필드를 요청한다 (예: `display_status` 또는 정책 단위 `satisfiable_from`).
  - 장점: FE에 판정 로직이 들어가지 않는다. Milestone 역할 경계와 맞는다.
  - 단점: BE 응답 스키마 변경이 필요하다.
- **선택지 B** — 카드에 보조 표시만 넣는다. 배지는 "조건 미충족"이되 "○○부터 가능" 한 줄을 덧붙인다.
  - 조건들의 `satisfiable_from` 중 가장 이른 날짜를 고르는 것도 **집계 계산**이다. 이것이 FE가 해도 되는 표시인지, BE가 줘야 하는 값인지 BE와 합의해야 한다.
  - 장점: 분류를 늘리지 않고 (라)를 해소한다.
- **선택지 C** — 현재대로 둔다. 상세에서만 확인한다.
  - 단점: 대시보드·필터에서 "향후 가능"이 사라진다.

**결정:** _(미정)_

> 함께 확정할 것: 이 날짜는 조건 충족 예상일일 뿐이므로 **접수 가능일로 표현하지 않는다** (공고 접수기간과 무관).

### S-3 · `NEEDS_INFO`와 `NEEDS_REVIEW`를 구분하는가 【미정】

현재는 둘 다 노란 계열로 보여 구분되지 않는다. 사용자의 다음 행동이 정반대인데도 그렇다.

- **선택지 A** — 배지는 `UNKNOWN` 하나로 두고 **다음 행동 버튼**으로만 구분한다.
  (`NEEDS_INFO` → "추가 질문 답하기" / `NEEDS_REVIEW` → 버튼 없이 담당부서 연락처)
  - 현재 상세 화면이 `NEEDS_REVIEW`에 담당부서 연락처를 이미 노출하고 있어 이 방향과 가깝다.
- **선택지 B** — 별도 배지를 추가해 분류를 늘린다.
- **선택지 C** — 배지는 같게 두고 카드에 보조 라벨 한 줄을 붙인다.

**결정:** _(미정)_

### S-4 · `ESTIMATED` · `NEEDS_REVIEW` 표시 【미정 · 우선순위 높음】

(가) 때문에 **가장 먼저 해소해야 할 항목**이다. 신뢰도는 판정 상태와 다른 시각 언어를 써야 한다.

- **선택지 A** — 색 없는 중성 칩. 테두리만 있는 회색 배지 + 한국어 문구.
  - 장점: 상태색과 절대 겹치지 않는다. 구현이 가장 작다.
  - 주의: 테두리만 쓰면 `--line-strong` 이상을 써야 3:1을 만족한다.
- **선택지 B** — 배지를 없애고 카드 하단 안내 문구 한 줄로 대체한다.
  - 현재 Dashboard에는 이미 "판정 신뢰도: … · 담당부서 확인이 필요합니다" 문구가 배지와 **중복**으로 들어가 있다. 배지를 빼면 중복이 해소된다.
- **선택지 C** — 아이콘 + 툴팁.
  - 모바일에서 툴팁이 불리하다. 권장하지 않는다.

함께 정할 사용자 문구 (**현재 enum 원문 노출 중**):

| enum | 사용자 문구 |
| --- | --- |
| `CONFIRMED` | 표시하지 않음 (기본값) |
| `ESTIMATED` | _(미정)_ 예: "추정 포함" |
| `NEEDS_REVIEW` | _(미정)_ 예: "확인 필요" |

**결정:** _(미정)_

### S-5 · 정책 제목 【미정】

현재 카드·상세 제목이 `policy_id` 원문이다.

- **선택지 A** — BE 판정 응답에 정책명을 포함해 달라고 요청한다.
- **선택지 B** — `GET /v1/policies/{id}`로 별도 조회해 채운다. (요청 수가 늘어난다)

**결정:** _(미정)_

## 5. 근거(Evidence) 표시 규격

모든 판정은 원문 근거와 연결돼야 한다 (Milestone 11장, 가장 중요한 품질 기준).

현재 구현(`renderJudgementDetail`)은 조건마다 `<blockquote>`에 `source_quote`를 넣고, URL이 있을 때만 "원문 보기" 링크를 덧붙인다.
스타일: 배경 `#f5f7f3`, 좌측 `3px solid #135f3c`, 패딩 16px.

### 확정된 것 (그대로 둔다)

- URL은 `rule.source_url` → `result.origin_url` → `null` 순으로 대체한다.
- **인용문 부재는 응답을 거부하고, URL 부재만 허용한다.** 근거 없는 확정 금지 원칙과 맞는다.
- 인용문은 원문 그대로 보여준다. 요약하거나 다듬지 않는다.
- 근거 없는 금액·기간·조건을 화면에 노출하지 않는다.

### S-6 · 원문 URL이 없을 때 【미정】

현재는 링크를 **그냥 생략**한다. 사용자는 링크가 없는 이유를 알 수 없다.

- **선택지 A** — 현재대로 생략한다. (시각적으로 가장 조용하다)
- **선택지 B** — "원문 링크 없음"을 명시한다.
- **선택지 C** — URL이 없는 근거를 신뢰도 표시와 연결한다 (S-4와 함께).

**결정:** _(미정)_

### S-7 · 긴 인용문 처리 【미정】

현재는 길이 제한 없이 전문을 표시한다. 조건이 많은 정책에서 상세 화면이 매우 길어진다.

- **선택지 A** — 현재대로 전문을 항상 표시한다.
- **선택지 B** — N줄에서 자르고 "더 보기"로 펼친다. (N = _미정_)
- **선택지 C** — 핵심 문장만 표시하고 원문 링크로 넘긴다.

**결정:** _(미정)_

### 조건 상세의 빈 문구

현재 조건 설명 `<p>`는 `FUTURE_PASS`(예상 충족일) 또는 영구 불충족일 때만 내용이 있고, 그 외에는 **빈 문단**이 남는다.
일반 `FAIL`·`PASS` 조건에 어떤 설명을 넣을지 정해야 한다 (빈 문단 자체를 없앨지 포함).

**결정:** _(미정)_

## 6. 카피 원칙

### `INELIGIBLE`을 Dead End로 만들지 않는다

PRD 2.1의 유지 항목이다. 조건 미충족 화면은 **거절 통보로 끝나면 안 된다.**

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| "신청할 수 없습니다" | "지금은 OO 조건이 맞지 않아요" |
| "자격 미달" | "OO이 △△이면 신청할 수 있어요" |
| 이유 없는 실패 | 미충족 조건 + 원문 근거 + 다음에 볼 것 |

`FAIL` 카드에서 항상 함께 제공할 것 (무엇을 넣을지는 _미정_):

- [ ] 어떤 조건 때문인지
- [ ] 향후 충족 가능한 조건인지 (S-2와 연결)
- [ ] 대안 정책으로 가는 경로

### 확정을 단정하지 않는다

- 중복수혜 확인 전에는 수혜 가능 조합이나 총 혜택 금액을 확정하지 않는다.
- 추정이 섞인 판정을 확정 문구로 쓰지 않는다.

| 결과 Dashboard | `#/results` | **실제 판정 API 연결됨.** 3칸 요약·정책 카드. `FUTURE_PASS` 분류 없음 |
| 정책 상세 | `#/policies/:id` | **연결됨.** 조건 4상태 배지 + 근거 blockquote + 담당부서 연락처 |
| 역질문 | `#/questions` | **연결됨.** 필드별 질문 병합, boolean/number/choice, 답변 후 재판정 |
| 조합 | `#/combinations` | **연결됨.** `conservative/maximal` 조합, 제외 정책의 충돌 근거 |
| 서류·일정 | `#/schedule` | 미연결. `POST /v1/plan` 대기 |

`YPC_API_BASE`가 설정된 서버 모드에서만 실제 요청을 보내고, 없으면 기존 Mock으로 동작한다.

### Design이 확인해야 할 미적용 스타일

새 화면들이 쓰는 아래 클래스에 **CSS 규칙이 없다.** 마크업에만 있고 스타일이 붙지 않은 상태다.

| 클래스 | 쓰이는 곳 |
| --- | --- |
| `.judgement-summary` | Dashboard 요약 3칸 |
| `.judgement-card` | 정책 카드 |
| `.question-card` | 역질문 카드 |
| `.conflict` | 조합 충돌 표시 |
| `.notice-inline` | 담당부서 확인 안내 |

`.card`·`.summary` 같은 공통 클래스와 함께 쓰여 기본 형태는 잡히지만, **구분을 위해 추가된 클래스가 아무 일도 하지 않는다.**
각 클래스에 스타일을 정의할지, 마크업에서 뺄지 정해야 한다. 특히 `.conflict`와 `.notice-inline`은 의미상 시각적 구분이 필요해 보인다.

### 남은 시안 작업

서류·일정 화면은 아직 구현 전이므로 시안이 먼저 필요하다. 나머지 화면은 구현이 앞서 있으므로 **시안보다 위 S 항목 확정과 스타일 보정이 우선**이다.
