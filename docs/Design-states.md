# 판정 상태 · 근거 표현 규격

갱신일: 2026-09-19 · 작성: Design · **초안, 결정 대기 항목 있음**

Milestone 11장 "반드시 고정할 인터페이스 4개" 중 **4번 `Design ↔ FE: 상태·근거 표현 규격`**에 해당하는 문서다.
판정 상태와 근거 UI를 화면마다 다르게 만들지 않기 위한 단일 기준이며, 판정 로직 자체는 정의하지 않는다.

이 문서의 결정 항목(S-1 ~ S-6)은 아직 비어 있다. **채워지기 전까지 FE는 해당 부분을 구현하지 않는다.**

## 1. 서버가 주는 값 (PRD 기준)

정책 단위 판정은 **두 축**으로 온다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| `verdict` | `ELIGIBLE` | 조건을 충족한다 |
| | `INELIGIBLE` | 조건을 충족하지 못한다 |
| | `NEEDS_INFO` | **사용자 정보**가 부족해 판정할 수 없다 |
| `confidence` | `CONFIRMED` | 원문 근거로 확정된 판정 |
| | `ESTIMATED` | 추정이 섞인 판정 |
| | `NEEDS_REVIEW` | **공고문·근거** 자체에 추가 검토가 필요하다 |

조건 단위 상태는 별도로 `PASS / FAIL / UNKNOWN / FUTURE_PASS` 4개다 (PRD 13장).

> **주의**: `NEEDS_INFO`는 *사용자가 답하면 풀리는 것*, `NEEDS_REVIEW`는 *사용자가 무엇을 해도 풀리지 않는 것*이다.
> 사용자의 다음 행동이 완전히 다르므로 같은 표현으로 뭉개지 않는다.

## 2. 화면 분류 4개 (현재 구현값)

`src/contracts.js`의 `statuses`가 쓰는 값이다. 색은 `src/styles.css`에 정의돼 있다.

| 키 | 문구 | 기호 | 글자색 | 배경색 | 다음 행동 |
| --- | --- | --- | --- | --- | --- |
| `PASS` | 신청 가능 | `✓` | `#135f3c` | `#dceee2` | 근거 확인 후 서류 준비 |
| `FAIL` | 조건 미충족 | `×` | `#993d36` | `#fae9e6` | 미충족 이유 확인 |
| `UNKNOWN` | 추가 확인 | `?` | `#775013` | `#fff3dc` | 추가 질문 답변 |
| `FUTURE_PASS` | 향후 가능 | `↗` | `#325975` | `#e5edf8` | 예상 충족일 확인 |

색만으로 구분하지 않고 **기호와 문구를 항상 함께** 제공한다. 위 4쌍의 명도 대비는 모두 WCAG AA를 통과한다 ([Design-system.md](Design-system.md) 6장).

## 3. 매핑 규칙 【S-1 · 미정】

`verdict` 3개와 `confidence` 3개의 조합 9가지를 위 4분류 중 무엇으로 보여줄지 확정해야 한다.
**FE는 이 표 없이 임의로 추측하지 않는다.**

| # | `verdict` | `confidence` | 화면 분류 | 비고 |
| --- | --- | --- | --- | --- |
| 1 | `ELIGIBLE` | `CONFIRMED` | | 가장 단순한 경우 |
| 2 | `ELIGIBLE` | `ESTIMATED` | | S-4와 연결 |
| 3 | `ELIGIBLE` | `NEEDS_REVIEW` | | 확정 표시 금지 대상 |
| 4 | `INELIGIBLE` | `CONFIRMED` | | S-2와 연결 |
| 5 | `INELIGIBLE` | `ESTIMATED` | | |
| 6 | `INELIGIBLE` | `NEEDS_REVIEW` | | |
| 7 | `NEEDS_INFO` | `CONFIRMED` | | |
| 8 | `NEEDS_INFO` | `ESTIMATED` | | |
| 9 | `NEEDS_INFO` | `NEEDS_REVIEW` | | S-3과 연결 |

제약 (PRD·Milestone에서 이미 고정된 것):

- 원문 근거가 없는 조건은 자동 확정하지 않는다 → 3·6번을 `PASS`/`FAIL`로 확정 표시할 수 없다.
- `UNKNOWN`을 임의로 `PASS`로 바꾸지 않는다.
- `ESTIMATED`를 확정 판정으로 표시하지 않는다.

## 4. 결정 항목 상세

### S-2 · `FUTURE_PASS`는 무엇으로 판별하는가 【미정】

서버 `verdict`에는 "향후 가능"에 해당하는 값이 없다. 그런데 화면 분류에는 있다.
`docs/Frontend-contract.md`가 **"미래 날짜 존재만으로 FE가 신청 가능 여부를 재판정하지 않는다"**고 못 박았으므로, 아래 중 하나를 골라야 한다.

- **선택지 A** — BE에 표시용 필드를 요청한다. 예: `display_status` 또는 `is_future_eligible`. FE는 그 값만 읽는다.
  - 장점: FE에 판정 로직이 전혀 들어가지 않는다. Milestone의 역할 경계와 가장 잘 맞는다.
  - 단점: BE 응답 스키마 변경이 필요하다.
- **선택지 B** — 합의된 파생 규칙을 이 문서에 명시하고 FE가 적용한다. 예: `verdict == INELIGIBLE && future_eligibility_date != null` → `FUTURE_PASS`.
  - 장점: BE 변경이 없다.
  - 단점: 표현 규칙과 판정 로직의 경계가 흐려진다. 규칙이 바뀌면 FE 코드를 고쳐야 한다.
- **선택지 C** — 화면 분류를 3개로 줄이고 "향후 가능"은 `INELIGIBLE` 카드 안의 보조 표시로만 둔다.
  - 장점: 매핑 문제가 사라진다.
  - 단점: 대시보드 상단 집계와 필터에서 "향후 가능"이 사라진다. PRD 2.1의 유지 항목과 충돌할 수 있다.

**결정:** _(미정)_

> 함께 확정할 것: 정책 전체의 `future_eligibility_date`와 개별 조건의 충족 예상일은 다른 값이다. 카드에 쓰는 것이 어느 쪽인지 명시한다.
> 또한 이 날짜를 **접수 가능일로 표현하지 않는다** (조건 충족 예상일일 뿐, 공고 접수기간과 무관).

### S-3 · `NEEDS_INFO`와 `NEEDS_REVIEW`를 구분하는가 【미정】

- **선택지 A** — 배지는 `UNKNOWN`(추가 확인) 하나로 같게 두고, **다음 행동 버튼**으로만 구분한다.
  (`NEEDS_INFO` → "추가 질문 답하기" / `NEEDS_REVIEW` → 버튼 없음 + "검토 중" 안내)
  - 장점: 배지 종류가 늘지 않는다. 상태 필터가 단순하다.
- **선택지 B** — 별도 배지를 추가해 5분류로 만든다.
  - 장점: 사용자가 목록에서 바로 구분한다.
  - 단점: 색·기호를 하나 더 정의해야 하고 대시보드 집계 칸이 늘어난다.
- **선택지 C** — 배지는 같게 두고 카드에 보조 라벨 한 줄을 붙인다.

**결정:** _(미정)_

### S-4 · `ESTIMATED` 신뢰도 표시 【미정】

현재 배지 컴포넌트(`.badge`)에는 신뢰도를 표현할 자리가 **아예 없다.**

- **선택지 A** — 배지 옆에 보조 칩을 붙인다. 예: `✓ 신청 가능` + `추정`
- **선택지 B** — 카드 하단에 안내 문구 한 줄. 예: "일부 조건은 추정입니다. 근거를 확인하세요."
- **선택지 C** — 배지 자체를 약화시킨다 (테두리만, 채움 없음).
  - 주의: 색 대비가 무너지기 쉽다. 채택 시 재측정 필요.

**결정:** _(미정)_

공통 제약: `CONFIRMED`에는 아무 표시도 붙이지 않는다 (기본값이므로 시각 노이즈를 만들지 않는다).

## 5. 근거(Evidence) 표시 규격

모든 판정은 원문 근거와 연결돼야 한다 (Milestone 11장 하단, 가장 중요한 품질 기준).

현재 구현 (`src/app.js`의 `detail()`): `<blockquote>` 안에 인용문 + 출처 각주.
스타일: 배경 `#f5f7f3`, 좌측 `3px solid #135f3c`, 패딩 16px.

필드는 `source_quote` / `source_url` / `confidence` 세 가지다.

### S-5 · 원문 URL이 없을 때 【미정】

현재 `mocks/scenario.json`의 URL은 **전부 `null`**이다. 실제 서비스에서도 누락될 수 있다.

- **선택지 A** — 인용문만 표시하고 링크 자리를 비운다.
- **선택지 B** — "원문 링크 없음"을 명시한다.
- **선택지 C** — URL이 없는 근거는 신뢰도를 낮춰 표시한다 (S-4와 연결).

### S-6 · 긴 인용문 처리 【미정】

- **선택지 A** — 전문을 항상 표시한다.
- **선택지 B** — N줄에서 자르고 "더 보기"로 펼친다. (N = _(미정)_)
- **선택지 C** — 핵심 문장만 표시하고 원문 링크로 넘긴다.

**결정:** _(미정)_

### 확정된 규칙

- 인용문은 **원문 그대로** 보여준다. 요약하거나 다듬지 않는다.
- 근거 없는 금액·기간·조건을 화면에 노출하지 않는다 (Milestone M4 완료 판정).
- 출처 각주에는 문서명과 위치를 함께 적는다.

## 6. 카피 원칙

### `INELIGIBLE`을 Dead End로 만들지 않는다

PRD 2.1의 유지 항목이다. 조건 미충족 화면은 **거절 통보로 끝나면 안 된다.**

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| "신청할 수 없습니다" | "지금은 OO 조건이 맞지 않아요" |
| "자격 미달" | "OO이 △△이면 신청할 수 있어요" |
| 이유 없는 실패 | 미충족 조건 + 원문 근거 + 다음에 볼 것 |

`FAIL` 카드에서 항상 함께 제공할 것 (무엇을 넣을지는 _미정_):

- [ ] 어떤 조건 때문인지
- [ ] 향후 충족 가능한 조건인지 (S-2와 연결)
- [ ] 대안 정책으로 가는 경로

### 확정을 단정하지 않는다

- 중복수혜 확인 전에는 수혜 가능 조합이나 총 혜택 금액을 확정하지 않는다.
- 추정이 섞인 판정을 확정 문구로 쓰지 않는다.

## 7. 적용 현황

| 화면 | 경로 | 상태 표현 적용 |
| --- | --- | --- |
| 결과 Dashboard | `#/results` | 4분류 배지·집계·필터 구현됨 (Mock 기준) |
| 정책 상세 | `#/policies/:id` | 조건별 배지 + 근거 blockquote 구현됨 |
| 역질문 | `#/questions` | 껍데기. 질문 타입 4종·건너뛰기 미구현 |
| 조합 | `#/combinations` | 충돌 사유가 평문 한 줄. 근거 연결 없음 |
| 서류·일정 | `#/schedule` | 체크 상태·타임라인 시각화 없음 |

위 3개 화면의 시안은 별도 작업이며, 이 문서의 S-1 ~ S-4가 확정된 뒤에 진행한다.
