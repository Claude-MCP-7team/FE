좋아. 계획서 내용을 기준으로 보면 이 프로젝트는 단순한 **‘청년정책 추천 서비스’**가 아니라,

> **사용자의 상황을 한 번 입력하면 → 정책 공고문을 AI가 해석하고 → 자격을 판정하고 → 불확실한 조건은 다시 질문하고 → 중복수혜 가능 여부까지 비교해서 → 최적의 정책 조합과 실제 신청 계획을 만들어주는 서비스**

로 정의하는 게 핵심이야. 계획서에서도 기존 서비스가 `찾아주기/적격·부적격 판정`에서 끝나는 문제를 지적하고, 이를 실제 행동까지 연결하는 것을 핵심 차별점으로 두고 있어. 

아래 PRD는 **Claude Code로 실제 구현할 때 그대로 개발 기준 문서로 사용할 수 있는 수준**으로 구체화했어. 특히 화면만 나열하지 않고 **기능 → AI 처리 → 데이터 → 예외 상황 → 판정 근거**까지 연결해서 작성했어.

# 2. Background

현재 청년정책 서비스는 정책 정보를 제공하거나 사용자의 조건에 따라 정책을 추천하는 기능을 제공한다.

그러나 실제 사용자가 정책을 신청하기 위해서는 단순한 정책 추천 이상의 과정이 필요하다.

계획서에서 직접 확인한 온통청년 자가진단 사례에서는 **7개 자격조건 중 6개를 충족했음에도 거주지역 조건 하나로 최종 결과가 단순히 ‘부적격’으로 종료**됐다. 사용자가 실제로 알고 싶은 것은 단순히 적격 여부가 아니라 **왜 안 되는지, 언제부터 가능해지는지, 대신 어떤 정책을 받을 수 있는지**이다. 

또한 현재 청년정책은 약 3,000개 규모로 제공되고 있어 사용자가 정책을 하나씩 찾아보아야 하며, 여러 정책 공고문에 흩어진 **중복수혜 제한 조건까지 사용자가 직접 비교해야 한다.** 

따라서 본 프로젝트는 기존의

**정책 검색 → 개별 자격 확인**

구조를

**개인 조건 입력 → 전체 정책 판정 → AI 역질문 → 근거 설명 → 정책 조합 최적화 → 서류 준비 → 신청 일정**

구조로 확장한다.

# 3. Problem Statement

## 3.1 문제 1 — 결과만 있고 설명이 부족하다

기존 자격진단 서비스는 사용자를 `적격 / 부적격 / 확인불가` 형태로 분류한다.

하지만 부적격인 경우에도 다음과 같은 정보가 필요하다.

* 어떤 조건 때문에 탈락했는가?
* 다른 조건은 충족했는가?
* 해당 조건은 앞으로 충족 가능한가?
* 언제부터 신청할 수 있는가?
* 대신 신청할 수 있는 정책은 무엇인가?

현재 서비스는 이러한 **다음 행동(Next Action)**을 충분히 제공하지 않는다.

---

## 3.2 문제 2 — 정책을 하나씩 찾아야 한다

사용자가 자신의 조건에 맞는 정책을 직접 검색하고 각각의 정책 상세 페이지에서 자격조건을 확인해야 한다.

즉,

`정책 검색 → 상세페이지 → 자격 확인 → 뒤로가기 → 다른 정책 검색`

과정이 반복된다.

본 서비스에서는 이 과정을

> **개인정보/조건 입력 1회 → 다수 정책 일괄 판정**

으로 변경한다.

계획서에서도 공고문을 구조화한 뒤 조건 입력 한 번으로 약 3,000개의 정책을 일괄 판정하는 구조를 제안하고 있다.

**⑥ 무엇을 준비해야 하는가?**

**⑦ 언제부터 준비해야 하는가?**

# 6. Core Value Proposition

서비스의 핵심 가치는 다음 흐름으로 정의한다.

**Find → Judge → Explain → Ask → Optimize → Plan**

즉,

**찾아주기 → 판정하기 → 설명하기 → 되묻기 → 조합하기 → 실행계획 만들기**

기존 서비스들이 주로 `Find`에 집중했다면 본 서비스는 이후 단계까지 하나의 AI Pipeline으로 연결한다.

계획서 역시 기존 온통청년·보조금24·민간 AI 서비스가 맞춤 추천 또는 통합 안내를 제공하지만 결국 **목록 제시 또는 개별 판정에서 종료되고, 정보를 개인 상황에 적용하여 행동으로 연결하는 단계가 사용자에게 남는다**고 분석하고 있다.

# 8. Functional Requirements

## FR-01. 사용자 프로필/조건 입력

### 목적

정책 판정에 필요한 사용자 정보를 한 번 입력받아 여러 정책에 재사용한다.

### 기본 입력값

| 항목 | 필수 여부 | 예시 | 판정 활용 |
| --- | --- | --- | --- |
| 생년월일 | 필수 | 2002-05-12 | 연령 기준 및 미래 자격시점 |
| 현재 거주지역 | 필수 | 경기도 용인시 | 지역 제한 |
| 연속 거주 시작일 | 필수 | 2024-03 | 거주기간 및 미래 충족일 자동 계산 |
| 학력·재학 여부 | 필수 | 대학 재학 | 학력·재학 조건 |
| 취업 상태 | 필수 | 미취업 | 취업·미취업 조건 |
| 근로 형태 | 필수 | 해당 없음 | 근로시간·고용형태 조건 |
| 개인 소득 | 필수 | 월 0원 | 개인 소득 기준 |
| 가구 소득 | 조건부 | 입력 또는 확인 필요 | 중위소득·건강보험료 기준 |
| 가구원 수 | 필수 | 3명 | 가구소득 기준 구간 계산 |
| 세대주 여부 | 필수 | 세대원 | 주거·독립 정책 조건 |
| 혼인 상태 | 필수 | 미혼 | 혼인 제한 조건 |
| 부모와 동거 여부 | 필수 | 동거 | 독립·가구 분리 조건 |
| 기존 정책 참여 여부 | 필수 | 있음/없음/모름 | 유사사업 제외조건 |
| 참여 이력 상세 | 참여 이력 존재 시 필수 | 사업명·기간·지원 내용 | 중복수혜 및 재참여 제한 교차판정 |
| 기존 지원금 수혜 | 조건부 | 국가장학금 | 중복수혜 제한 교차판정 |

중요한 점은 **고정 입력 폼만으로 모든 정보를 받지 않는다**는 것이다.

계획서에서 지적한 것처럼 실제 공고문에는 `6개월 이상 계속 거주`, `부모 합산 소득`, `타 유사사업 참여 이력 없음` 등 고정된 8개 필터만으로 표현하기 어려운 조건이 존재한다. 

따라서 초기 입력은 **판정에 반복적으로 필요한 공통조건만 수집**하고 나머지는 AI 역질문으로 해결한다.

### 입력 UX 원칙

1. 입력 폼은 `기본·거주 → 학업·취업 → 가구·참여 이력 → 검토` 단계로 나눈다.
2. 현재 단계와 전체 진행률을 표시하고 단계별 입력값을 임시 저장한다.
3. 연속 거주 시작일을 입력하면 기준일 현재 거주 개월 수를 자동 계산한다.
4. 참여 이력이 `있음`이면 사업명, 운영기관, 참여기간, 지원 내용을 추가 입력받는다.
5. 참여 이력이 `잘 모르겠음`이면 적격으로 확정하지 않고 `UNKNOWN`으로 유지한 뒤 AI가 정책별로 되묻는다.
6. 취약계층, 병역, 재산은 전 사용자에게 일괄 요구하지 않는다. 해당 조건이 있는 정책을 발견했을 때만 질문하며 질문 목적과 사용 범위를 설명한다.
7. 필수값 누락 시 저장하지 않고 해당 필드 가까이에 오류와 해결 방법을 표시한다.

# 11. FR-04. AI 자격 판정 Engine

정책별 모든 조건을 사용자 프로필과 비교한다.

단순 Boolean 판정이 아니라 조건별 상태를 가진다.

```text
PASS
FAIL
UNKNOWN
FUTURE_PASS
```

예를 들어,

```text
나이              PASS
소득              PASS
취업상태          PASS
학력              PASS
거주지역          PASS
6개월 이상 거주   FAIL
```

이면 단순히

> ❌ 부적격

으로 끝내지 않는다.

### 결과

> 현재는 거주기간 조건으로 신청할 수 없습니다.

> 나머지 주요 자격조건은 충족하고 있습니다.

> 현재 거주기간: 4개월

> 필요 거주기간: 6개월

> **약 2개월 후 거주기간 조건을 충족할 가능성이 있습니다.**

---

# 12. FR-05. Explainable Eligibility

모든 AI 판정에는 **근거가 존재해야 한다.**

정책 상세화면에서 다음 형태로 표시한다.

### 자격조건

| 조건   | 결과 | 근거       |
| ---- | -- | -------- |
| 나이   | ✓  | 만 19~34세 |
| 지역   | ✓  | 용인시 거주   |
| 취업   | ✓  | 미취업      |
| 소득   | ✓  | 기준 이하    |
| 거주기간 | ✕  | 6개월 미충족  |

그리고 각 조건을 누르면

> **공고문 근거**

를 확인할 수 있도록 한다.

AI가 임의로 판단한 것처럼 보이지 않게 하는 것이 중요하다.

# 13. FR-06. AI 역질문

이 프로젝트에서 가장 중요한 차별화 기능 중 하나다.

AI가 `UNKNOWN` 조건을 발견하면 사용자를 탈락시키지 않는다.

### 예시

정책 조건:

> 최근 2년 내 유사 청년취업지원사업 참여자는 제외

사용자 데이터:

```text
관련 정보 없음
```

### 기존 시스템

```text
확인불가
```

# 17. FR-10. 정책 대안 추천

```text

이유
→ 용인시 6개월 이상 거주 조건 미충족

③ 대학생 생활지원 사업
```

**FAIL → END**

# 19. FR-12. 정책 조합 최적화

단순히 정책 하나를 추천하지 않는다.

신청 가능한 정책들의 조합을 생성한다.

예:

```text
A 정책 : 300만원
B 정책 : 200만원
C 정책 : 100만원
```

중복조건:

```text
A + B 불가능
A + C 가능
B + C 가능
```

가능 조합:

```text
A          300만원
B          200만원
C          100만원
A + C      400만원
B + C      300만원
```

따라서:

### AI 추천

> **A + C 정책 조합**

> 예상 최대 지원 규모
> **400만원**

계획서가 기존 정책 매칭과 가장 명확하게 차별화하는 지점이다. 정책을 독립적으로 추천하는 것이 아니라 **중복수혜 제한을 교차 판정하여 ‘무엇을 받아야 유리한가’에 답하도록 설계**되어 있다.

# 23. AI Multi-Agent Architecture

계획서에서 Claude Code 멀티에이전트를 핵심 도구로 사용하고 **5개의 서브에이전트**를 제안하고 있다. 

이를 실제 개발 구조로 다음과 같이 정의한다.

```text
                  Orchestrator Agent
                         │
       ┌─────────────────┼─────────────────┐
       ↓                 ↓                 ↓
 Parsing Agent     Eligibility Agent   Question Agent
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ↓
                  Optimization Agent
                         │
                         ↓
                    Schedule Agent
```

### Agent 1 — Parsing Agent

공고문 → Structured Policy JSON

담당:

* 자격조건
* 제외조건
* 중복수혜조건
* 필요서류
* 신청기간

추출.

### Agent 2 — Eligibility Agent

```text
UserProfile
        ×
PolicyConditions
```

비교.

결과:

```text
PASS / FAIL / UNKNOWN
```

### Agent 3 — Question Agent

UNKNOWN 조건 발견 시 사용자에게 필요한 질문 생성.

### Agent 4 — Optimization Agent

가능 정책들의 중복수혜 관계를 분석하고 최적 조합 계산.

### Agent 5 — Schedule Agent

마감일과 서류 발급기간을 기반으로 준비 일정을 역산.

# 24. AI Cross Validation

자격 판정 오류는 사용자의 실제 금전적 손실로 이어질 수 있기 때문에 계획서에서는 **2개 Agent의 독립 판정**을 제안하고 있다. 

구조:

```text
Policy
   │
 ┌─┴─────────────┐
 ↓               ↓
Judge Agent A    Judge Agent B
 ↓               ↓
Result A         Result B
 └──────┬────────┘
        ↓
     Compare
        ↓
 ┌──────┴───────┐
일치             불일치
 ↓                ↓
확정          사용자 확인
```

라고 표현한다.

```text
신청 기간
```


또는

```text

```

상태를 반환한다.

# 34. 기존 서비스와의 차별성

| 기능        | 기존 정책 서비스 | 본 서비스 |
| --------- | --------- | ----- |
| 정책 검색     | O         | O     |

| 미래 자격시점   | X         | **O** |
| 대안 정책     | 제한적       | **O** |
| 중복수혜 교차판정 | X         | **O** |
| 최적 정책 조합  | X         | **O** |

# 38. 기대효과

계획서에서 기대효과를 **사회적·경제적·일상생활 개선** 세 영역으로 정의하고 있다.

사회적으로는 정책 탐색 능력이 아니라 실제 자격조건이 수혜 여부를 결정하도록 하여 **정보 접근성 격차를 줄이는 것**을 목표로 한다.

> **“부적격”**

이라는 결과를

> **“6개월 후 신청 가능하며, 그전에는 이 정책을 신청하세요.”**

라는 **실행 계획으로 전환하는 것**이 최종 목표다.

# 41. FR-16. 단계형 조건 입력 및 재분석

### 목적

사용자가 최소한의 부담으로 판정에 필요한 정보를 정확히 입력하고, 변경한 조건이 결과에 어떻게 반영됐는지 이해하게 한다.

### 요구사항

```text
Step 1 기본·거주
→ Step 2 학업·취업
→ Step 3 가구·참여 이력
→ Step 4 입력 내용 검토
→ 정책 재분석
→ 변경 결과 요약
```

재분석 완료 후 다음 내용을 제공한다.

```text
변경된 입력
거주기간 4개월 → 7개월

변경된 결과
신청 가능 +2개
확인 필요 -1개

상태가 달라진 정책
용인 청년 주거지원: 곧 가능 → 신청 가능
```

### Acceptance Criteria

- 필수 입력이 누락되면 재분석을 실행하지 않는다.
- 조건 수정 결과가 상단 요약, 정책 카드, 조합, 서류, 일정에 동시에 반영된다.
- 입력값과 계산 기준일을 결과 화면에서 다시 확인할 수 있다.
- 분석 중에는 진행 상태를 보여주고 중복 실행을 방지한다.
- 실패 시 기존 결과를 유지하고 재시도 방법을 제공한다.

# 42. FR-17. 선택적 AI 역질문 확장

### 질문 대상

| 분류 | 질문 발생 조건 | 결과 활용 |
| --- | --- | --- |
| 취약계층 | 공고문에 기초생활수급·차상위·한부모·보호종료 조건 존재 | 우대·별도 소득기준 판정 |
| 병역 | 병역기간에 따른 연령 상한 연장 조항 존재 | 현재 및 미래 연령 판정 |
| 재산 | 부동산·자동차·금융자산 한도 존재 | 주거·자산형성 정책 판정 |
| 참여 이력 | 유사·동일 사업 참여자 제외 조항 존재 | 제외조건 및 중복수혜 판정 |

### UX 규칙

- 한 화면에서는 한 가지 판단만 묻는다.
- 질문 위에 `왜 필요한가`를 한 문장으로 설명한다.
- 답변마다 `해당 없음`, `잘 모르겠음`을 제공한다.
- 민감정보는 해당 정책 판정에만 사용한다는 범위를 명시한다.
- `잘 모르겠음` 선택 시 PASS 또는 FAIL로 임의 확정하지 않는다.
- 답변 후 상태가 변경된 정책과 변경 이유를 즉시 보여준다.
- 사용자는 프로필에서 저장된 추가 답변을 확인·수정·삭제할 수 있다.

# 43. FR-18. 판정 신뢰도 및 데모 데이터 표시

화면에 표시되는 모든 정책 정보는 다음 상태 중 하나를 가져야 한다.

```text
DEMO          예시 데이터
SOURCE_BASED  원문 근거가 연결된 자동 판정
USER_CONFIRM  사용자 답변이 필요한 판정
AGENCY_CHECK  운영기관 확인이 필요한 판정
```

### 표시 원칙

- 데모 데이터에는 화면 상단과 정책 카드에 `예시 결과`를 표시한다.
- `조건 일치도 96%`처럼 의미가 불명확한 점수는 제거한다.
- 대신 `필수조건 6개 중 5개 충족, 1개 확인 필요` 형태로 표시한다.
- 지원금에는 `예상 최대`, 지급 주기, 현금·현물·서비스 유형을 표시한다.
- 모든 판정에는 공고문 이름, 원문 문장, 페이지·조항, 수집일, 원문 링크를 제공한다.
- 다음 고지문을 결과 및 조합 화면에 표시한다.

> AI 판정은 신청 가능성을 안내하는 참고 정보이며, 최종 자격과 지급액은 운영기관의 심사 결과에 따라 달라질 수 있습니다.

# 44. FR-19. 중복수혜 교차판정 상세 UX

정책 조합 화면은 총액만 보여주지 않고 정책 쌍별 비교 근거를 제공한다.

### 판정 상태

```text
COMPATIBLE       동시 수혜 가능 근거가 명확함
CONFLICT         동시 수혜 불가 조항이 명확함
POSSIBLE_CONFLICT 유사사업 표현으로 충돌 가능성이 있음
UNKNOWN          원문만으로 판단 불가
```

### 정책 쌍 상세

```text
국민취업지원제도 × 경기 청년 면접수당

판정
동시 수혜 가능성 높음

정책 A 근거
공고문명 / 조항 / 원문

정책 B 근거
공고문명 / 조항 / 원문

AI 해석
면접수당은 실비성 지원으로 유사 구직촉진수당 제한에 해당하지 않음

다음 행동
운영기관 확인 / 공식 원문 열기
```

### Acceptance Criteria

- 조합에 포함된 모든 정책 쌍을 비교한다.
- 원문 근거가 없는 조합은 `동시 수혜 가능`으로 확정하지 않는다.
- 한 정책의 상태가 변경되면 전체 조합과 예상 혜택을 다시 계산한다.
- 현금, 포인트, 이자지원, 교육 서비스 등 서로 다른 혜택을 단순 합산하지 않는다.
- 사용자가 `최대 혜택`, `신청 가능성`, `준비 간편`, `빠른 신청` 기준을 선택할 수 있다.

# 45. FR-20. 정책 탐색 및 결과 변화 UX

### 정책 목록

- 정렬: 마감 임박순, 예상 혜택순, 신청 가능성순, 최근 공고순
- 필터: 판정 상태, 정책 분야, 주관기관, 신청 방식
- 사용자 행동: 관심 정책 저장, 확인한 정책 숨기기, 비교 목록 추가
- 카드 핵심 정보 순서: `판정 상태 → 정책명 → 혜택 → 마감일 → 핵심 판정 이유`

### 상태 변화 피드백

AI 질문 또는 조건 수정 후 단순 토스트만 표시하지 않는다.

```text
답변을 반영했습니다.

청년도전지원사업
확인 필요 → 신청 가능

이유
최근 2년 내 유사사업 참여 이력이 없다고 답변했습니다.
```

상태가 변경된 카드는 결과 목록 상단에서 일시적으로 강조하고, 사용자가 변경 내용을 확인한 뒤 원래 정렬로 복귀할 수 있게 한다.

# 46. FR-21. 신청 실행 상태 관리

정책별 진행 상태를 다음과 같이 분리한다.

```text
관심 정책
→ 조건 확인
→ 서류 발급 중
→ 서류 준비 완료
→ 신청서 작성 중
→ 제출 완료
→ 접수 확인
```

각 서류에는 발급처, 발급 링크, 예상 소요일, 유효기간, 사용 가능한 정책을 표시한다. 사용자는 권장 준비일과 마감일을 캘린더에 저장하고 알림을 설정할 수 있어야 한다.

# 47. UI 접근성 및 사용성 요구사항

### Accessibility

- 텍스트와 배경 명암은 WCAG 2.1 AA 기준을 충족한다.
- 상태는 색상만으로 전달하지 않고 아이콘과 문구를 함께 사용한다.
- 모든 기능은 키보드만으로 이용할 수 있어야 한다.
- 모달이 열리면 첫 입력 요소로 포커스를 이동하고 닫으면 실행 버튼으로 돌려보낸다.
- 동적으로 변경된 판정 결과는 스크린리더에 한 번만 안내한다.
- 200% 확대 및 320px 화면에서도 내용이 겹치거나 잘리지 않는다.

### Usability Test Tasks

1. 사용자가 처음 방문해 조건 입력을 완료할 수 있는가?
2. 특정 정책이 부적격인 핵심 이유를 10초 안에 찾을 수 있는가?
3. AI 질문에 답한 후 변경된 정책을 찾을 수 있는가?
4. 추천 조합의 중복수혜 근거와 불확실성을 설명할 수 있는가?
5. 필요한 서류와 첫 준비일을 찾을 수 있는가?

MVP 사용자 테스트 목표:

```text
조건 입력 완료율 ≥ 80%
핵심 부적격 사유 발견 성공률 ≥ 90%
AI 질문 후 상태 변화 인지율 ≥ 90%
추천 조합 근거 이해율 ≥ 80%
서류·일정 확인 과업 성공률 ≥ 90%
```

# 48. 수정된 MVP 구현 우선순위

### Phase 1 — 신뢰 가능한 판정 기반

1. 실제 정책 데이터와 원문 출처 연결
2. 필수 사용자 조건과 단계형 입력
3. 조건 변경에 따른 실제 재판정
4. PASS / FAIL / UNKNOWN / FUTURE_PASS 처리
5. 데모·실제 데이터 구분 및 면책 고지

### Phase 2 — 핵심 차별 기능

1. 선택적 AI 역질문
2. 답변 후 결과 변화 표시
3. 부적격 사유 및 미래 자격시점
4. 중복수혜 정책 쌍 교차판정
5. 근거가 연결된 최적 조합

### Phase 3 — 신청 실행 지원

1. 필요 서류와 발급 링크
2. 신청 일정 역산
3. 관심 정책·진행 상태 저장
4. 마감 알림·캘린더 연동
5. 모바일 및 접근성 사용자 테스트
